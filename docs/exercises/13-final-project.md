# 課題13: 最終課題(レビュー・品質改善・ライブテスト)

**週12(課題12と並行)** / コードを新しく書くより、**読む・説明する・改善する**課題

## 1. 課題の目的

自分が作ったものを、**他人(未来の自分を含む)に説明できる**状態にする。完成形と読み比べ、違いの理由を理解し、品質を上げる。

## 2. 学習する概念

コードレビュー / 設計の説明とトレードオフ / リファクタリング / 保守性・可読性 / 運用を考える(監視・障害対応・スケール)

## 3. 背景知識

レビューの観点(自分のコードを、他人のコードのように読む):

| 観点           | 問い                                                                                           |
| -------------- | ---------------------------------------------------------------------------------------------- |
| 正しさ         | 異常系(失敗・空・巨大・重複)で動く?競合(`await` の間に割り込まれたら)は?                       |
| 型             | `any` / `as` / `!`(non-null assertion)を使っていないか。使うなら、理由を説明できるか           |
| 責務           | 1つの関数・クラスが、2つ以上の理由で変更されないか。ハンドラにビジネスロジックが入っていないか |
| 依存           | 実装クラスを `new` している場所は?差し替えられる?                                              |
| エラー         | 利用者に返す/ログに残す/握りつぶす の判断は適切か。内部情報が漏れていないか                    |
| セキュリティ   | 入力の検証は?秘密はログ・エラー・コミットに無いか?                                             |
| テスト         | 異常系のテストがある?**このテストはバグを見つけられる?**(ミューテーションの視点)               |
| 名前・コメント | 名前が意図を表している?コメントは「なぜ」を書いている?(「何を」はコードで)                     |

## 4. 実装する機能(作業)

### A. 全検査を通す

```bash
npm run verify      # 型・lint・フォーマット・テスト・カバレッジ・受け入れテスト・ワークフロー検査・秘密検査・演習の検証・npm audit
```

starter の受け入れテストは `npm run exercise` で全て ✅ にする。

### B. 完成形と読み比べる(**ここで初めて `reference/` を読む**)

自分の `starter/` と `reference/` の**同じファイル**を並べて、次を表にする(違いは `git diff --no-index starter/src reference/src` で見られるが、`starter` は穴あきなので、**自分が実装した部分**の違いを見る)。

| ファイル             | 違い                             | どちらが良い?理由     | 自分の実装を直す? |
| -------------------- | -------------------------------- | --------------------- | ----------------- |
| (例)`async/retry.ts` | 待ち時間の計算を別関数にしている | 完成形:テストしやすい | 直す              |

「完成形の方が良い」と決めつけない。**自分の方が良い所**も探す。[ADR](../adr/README.md)を読み、自分の設計判断と違った点を整理する。

### C. セルフレビュー

上の観点で、自分の実装を**1ファイル**選んでレビューコメントを5個書く(PRのコメントとして)。1つは「**この設計のトレードオフ**」についてのコメントにする。

### D. 改善を1つ実装する

レビューで見つけた改善を1つ、**テストを先に書いて**実装する(リファクタリングなら、テストが緑のまま)。

### E. 動かして確かめる

```bash
cp .env.example .env
npx tsx starter/src/main.ts
# 別のターミナルで、docs/development-environment.md の curl を実行
# ① 同じ Idempotency-Key で2回 ② 内容を変えて同じキー ③ simulate-rate-limit ④ プロセスを kill -9 して再起動
```

`sqlite3 data/app.sqlite 'select id,status,error_code from provisioning_requests'` で、状態が思ったとおりか確認。

### F.(任意・注意)ライブテスト

**実際の GitHub にリポジトリを作ります。** 専用の検証用 Owner・権限を絞ったトークンで、[testing-strategy.md の「ライブテスト」](../testing-strategy.md#7-ライブテスト実githubapiを使う-任意明示的)の条件をすべて満たしてから実行する。

```bash
RUN_LIVE_GITHUB_TESTS=1 LIVE_GITHUB_OWNER=<検証用Owner> LIVE_GITHUB_OWNER_TYPE=organization \
LIVE_GITHUB_CONFIRM=<検証用Owner> GITHUB_TOKEN=<専用トークン> npm run test:live
```

終わったら、検証用リポジトリが削除されたこと(または手動で削除したこと)を確認し、**トークンを失効**させる。

## 5. 実装対象ファイル

自分が選んだファイル(D)。それ以外は読むだけ。

## 6. 受け入れ条件

- [ ] `npm run exercise` が全て ✅、`npm run verify` が通る
- [ ] B の比較表を書いた(5行以上)。自分の方が良いと思う点を**1つ以上**挙げた
- [ ] C のレビューコメントが5個ある。うち1つは、設計のトレードオフについて
- [ ] D の改善が、テストつきで入っている
- [ ] E で、冪等性(同じキーで2回)と、障害(`simulate-*`)の挙動を**実際に確かめた**
- [ ] 次の「最終確認の問い」に、**何も見ずに**答えられる

## 7. テスト方法

```bash
npm run verify
npm run exercise
```

## 10. 完了後に理解しておくべきこと

- 設計とは、**選択肢を比べ、トレードオフを理解したうえで選び、理由を残す**こと(ADR)
- 「完成形と同じ」である必要はない。**理由を説明できる違い**は価値
- 品質は、テスト・型・レビュー・CI・セキュリティの**重ね合わせ**で守る
- 本番で運用するなら、何が足りないか(認証・監視・バックアップ・スケール・秘密管理・SLO)を挙げられる
