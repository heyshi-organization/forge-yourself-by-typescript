# 課題11: セキュリティ演習

**週11** / 実装場所: `lab-workspace/<演習>/`(**`exercise/*` ブランチ**にだけ作られる)/ 教材: [`security-labs/`](../../security-labs/README.md)

## 1. 課題の目的

代表的な脆弱性を、**自分で攻撃を確認し、修正し、テストで確かめ**、CodeQL などのツールが**何を検出し、何を検出しないか**を実際に見て理解する。
(そして、セキュアな開発プロセス — 入力検証・秘密の管理・依存関係・CI — を、これまでの課題で体験した内容と結びつける)

## 2. 学習する概念

SQLインジェクション / コマンドインジェクション / パストラバーサル / 入力検証の不備(Mass Assignment)/ 秘密情報のハードコード / エラー情報の漏洩 / 認可の欠如(IDOR)/ SSRF / SAST(CodeQL)の仕組みと限界 / SCA / Secret Scanning / 多層防御 / 許可リスト

## 3. 背景知識

### 安全のためのルール(重要)

- 演習用の脆弱なコードは、**`.txt` として保管**されており、`main` では実行・ビルド・解析されません。`npm run lab:start` が、**あなたの `exercise/*` ブランチ**にだけ展開します(→ [ADR-0013](../adr/0013-security-labs-isolation.md))
- **`exercise/*` ブランチを `main` にマージしない**。CI(Exercise Guard)がPRを失敗させます。CodeQL の結果を見たら、PRを閉じてブランチを削除する
- 脆弱なコードを**ネットワークに公開しない**(テストの `app.inject()` で動かすだけ)。他人のシステムへの攻撃の練習はしない
- **実在のトークン・パスワードを使わない**(Secret Scanning の確認にも使わない)

### 演習の進め方(1テーマあたり)

```bash
npm run lab:start -- 01              # exercise/sec-01-sql-injection ブランチを作り、lab-workspace/ に展開
npm run lab:test -- 01               # テストが失敗する = 脆弱性がある
# lab-workspace/01-sql-injection/app.ts を修正 → npm run lab:test -- 01 が全部通るまで
git add lab-workspace && git commit -m "lab: 01 を修正" && git push -u origin HEAD
gh pr create --draft --fill          # ドラフトPR → CodeQL の結果を見る(Security タブ / PRのチェック)
# 結果を確認し、READMEの「CodeQLの検出結果」の欄と比べる → PRを閉じ、ブランチを削除
git switch main && git branch -D exercise/sec-01-sql-injection
```

各テーマの `README.md`(`security-labs/<演習>/README.md`)に、①脆弱な実装 ②理由 ③攻撃シナリオ ④CodeQLでの検出 ⑤修正方法 ⑥修正後のテスト ⑦検出できないケースと限界 があります。**修正方法は最後に読む**こと(先に自分で修正する)。

### 追加の作業(コードを書かない)

1. **自分の `starter/` に `npm audit`**: `npm audit --omit=dev` の結果の読み方(深刻度・経路・修正版)を確認する
2. [security-design.md](../security-design.md) を読み、**自分のこれまでの実装**で、どの脅威にどの対策を入れたか、対応表を自分で作る
3. [github-settings.md](../github-settings.md) を見て、自分のリポジトリで Secret Scanning / Push Protection / Dependabot を有効にする

## 5. 実装対象ファイル

`lab-workspace/<演習ID>/app.ts`(`npm run lab:start` で作られる。**テスト `security.test.ts` は変更しない**)

## 6. 受け入れ条件

- [ ] 取り組んだ各演習で、`npm run lab:test -- <ID>` が**全部通る**(攻撃が防がれ、**正常な利用も壊れていない**)
- [ ] 各演習について、**なぜその脆弱性が起きるか**を自分の言葉で説明できる
- [ ] 各演習で、CodeQL が**検出した/しなかった**を確認し、その理由(データの流れが追えるか)を説明できる
- [ ] `exercise/*` ブランチを `main` にマージしていない
- [ ] 実在の秘密・個人情報を、演習やPRに含めていない(`npm run check:secrets`)

## 7. テスト方法

```bash
npm run lab:start -- <ID>        # 展開(ブランチ作成)
npm run lab:test -- <ID>         # 演習のテスト
npm run exercise -- 11           # 全演習の状況
npm run lab:verify               # (メンテナ向け)演習自体の健全性: 脆弱版で攻撃テストが失敗 / 修正版で全部成功
```

## 8. 段階的なヒント

演習ごとのヒントは `security-labs/<演習>/README.md` の「ヒント」を参照。共通の考え方:

<details><summary>ヒント1: 入力を信用しない</summary>

外部から来る値は、**どこで・何として**使われるか(SQL・シェル・パス・URL・HTML…)を考える。使われる場所ごとに、解釈される特殊文字が違う。

</details>

<details><summary>ヒント2: 「構造」と「データ」を分ける</summary>

インジェクションの根本原因は、**命令(構造)とデータが同じ文字列に混ざる**こと。データを別の経路(バインド変数・引数配列)で渡せば、データは命令として解釈されない。

</details>

<details><summary>ヒント3: 許可リストと多層防御</summary>

危険なものを禁止する(拒否リスト)より、**許可するものを決める**(許可リスト)。そして1つの対策に頼らず、入力検証 + 安全なAPI + 解決後の確認…と重ねる。

</details>

## 9. 発展課題

1. 自分で新しい脆弱な例(ReDoS、プロトタイプ汚染、XSS など)を作り、CodeQL が検出するか調べて、`security-labs/` と同じ形式で追加する
2. 修正前のコードで、**CodeQL が検出しない**ケースを1つ見つけ、なぜ見つけられないか考える(データの流れが切れる? 間接的?)
3. 依存パッケージに脆弱性があるバージョンを `npm install` した PR を作り、Dependency Review が止めることを確認する(**確認後、PRは閉じる**)
4. `git log -p` で、秘密が一度コミットされると、後から消しても履歴に残ることを(ダミー値で)確認し、「まず無効化する」理由を説明する

## 10. 完了後に理解しておくべきこと

- インジェクション系の本質は「**構造とデータの混在**」。対策は、**混ぜない API**(バインド変数・引数配列)を使うこと
- 入力検証は**許可リスト**。型(`as`)は検証ではない(課題04)
- **認証**(誰か)と**認可**(何をしてよいか)は別。クライアントが送る値(ヘッダ・ID)で権限を決めない
- エラーメッセージ・ログ・設定・リポジトリは、**情報の出口**。何を出さないかを決める
- **SAST は万能ではない**。データの流れが追える脆弱性は強いが、**ロジックの欠陥(認可の抜け等)は検出できない**。ツールの結果を鵜呑みにせず、検出しないものは設計・レビュー・テストで守る
- SCA・Secret Scanning・Dependabot は、**自分のコードではない部分・うっかり**を守る補完的な仕組み
