# ADR-0005: GitHub API の認証方式

- 状態: 採用
- 日付: 2026-11-25

## 選択肢

| 案                                               | メリット                                                  | デメリット                                                               |
| ------------------------------------------------ | --------------------------------------------------------- | ------------------------------------------------------------------------ |
| A. 個人のクラシックPAT                           | 簡単                                                      | 権限が広すぎる(全リポジトリ)。漏洩時の被害が大きい                       |
| B. **fine-grained PAT(環境変数 `GITHUB_TOKEN`)** | 対象Owner・権限を絞れる。期限を設定できる。ローカルで完結 | 人に紐づく。定期的に更新が必要                                           |
| C. GitHub App(インストールトークン)              | 組織向けの本命。短命トークン・細かい権限・人に紐づかない  | 秘密鍵の管理、JWT→インストールトークンの実装が必要。学習の本筋から外れる |
| D. OAuth(ユーザーごとのトークン)                 | 利用者の権限で動かせる                                    | Webアプリのフロー(リダイレクト等)が必要。本サービスの範囲外              |

## 決定: B(将来 C へ)

- トークンは**環境変数 `GITHUB_TOKEN` からのみ**読む(`.env` は Git 管理外。`.env.example` はダミー値のみ)
- 必要な権限は最小にする(対象Ownerだけ・リポジトリ作成に必要な権限だけ・有効期限つき)。必要な権限の正確な一覧は、GitHub公式ドキュメントの「Create an organization repository」「Create a repository for the authenticated user」の _Fine-grained access tokens_ の欄で確認すること(**この教材の作成時には公式ドキュメントでの確認までは行っていない=未検証**)。ライブテスト用のトークンは**テスト専用Ownerだけ**に絞る
- トークンは `OctokitGitHubClient` の内部にだけ持ち、ログ・エラー・レスポンスに出さない(ADR-0012、テストあり)
- `GitHubClient` インターフェースで隠しているので、C への移行は `OctokitGitHubClient` の差し替えだけで済む

## Owner の指定方法

入力に `ownerType`(`user` / `organization`)を**必須**にした。
自動判定(`GET /users/{owner}` の `type`)は追加の API 呼び出しと失敗パターンを増やすため。
`ownerType=user` の場合は、認証ユーザーと `owner` が一致するか確認し、違えば `OWNER_MISMATCH`(422)にする
(GitHub は `POST /user/repos` で他人のOwnerを指定できないため、黙って別のOwnerに作られるのを防ぐ)。
