# ADR-0003: 依存性の注入(DI)

- 状態: 採用
- 日付: 2026-11-25

## 背景

「DI を利用して依存関係を管理する」ことが要件。一方で「不要な抽象化を増やさない」「学習対象でない技術に時間を使いすぎない」。

## 選択肢

| 案                                                 | メリット                                               | デメリット                                                                                           |
| -------------------------------------------------- | ------------------------------------------------------ | ---------------------------------------------------------------------------------------------------- |
| A. DIコンテナ(tsyringe / InversifyJS / NestJS等)   | 大規模で便利                                           | デコレータ・リフレクションなど**仕組みの学習コストが大きく**、DIの本質(依存を外から渡す)が見えにくい |
| B. **コンストラクタ注入 + Composition Root(手動)** | DIの本質だけを学べる。型チェックで配線ミスを検出できる | 依存が増えると配線コードが長くなる                                                                   |
| C. モジュールのグローバル import / シングルトン    | 簡単                                                   | テストで差し替えにくい(`vi.mock` に頼る)。依存関係が見えない                                         |

## 決定: B

- クラスは必要なものを**コンストラクタ引数のインターフェース**で受け取る(`ProvisioningServiceDeps` など)
- `composition.ts` の `buildContainer(config, overrides)` が、設定から本物の実装を組み立てる唯一の場所
- テストは `overrides` で `requests` / `provisioner` / `github` / `clock` / `ids` / `sleep` を差し替える
- **時計(`Clock`)・ID生成(`IdGenerator`)・待機(`sleep`)・乱数(`random`)も注入**する。時間やランダム性に依存するコードを決定的にテストするため

## 結果

- 配線が1か所に集まり、`new` が散らばらない(`grep -rn "new SqliteRequestRepository"` が1件)
- 依存が20〜30を超えるようになったら、コンテナの導入を再検討する(その時点で ADR を更新)
