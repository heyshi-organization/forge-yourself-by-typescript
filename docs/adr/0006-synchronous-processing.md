# ADR-0006: 非同期処理の設計(リクエスト内で同期処理する)

- 状態: 採用
- 日付: 2026-11-25

## 背景

リポジトリ作成は GitHub への外部呼び出し(数百ms〜数秒、リトライで十数秒)を伴う。
HTTP の返し方(完了まで待つ / 受付だけして後で処理)と、状態の持ち方を決める。

## 選択肢

| 案                                                                                          | メリット                                                                  | デメリット                                                                                              |
| ------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| A. **同期処理**: POST の中で処理し、結果(201 / エラー)を返す。状態は DB に残す              | シンプル。クライアントは1回の呼び出しで結果が分かる。キュー・ワーカー不要 | 最悪ケースで応答に十数秒かかる。プロセスが途中で落ちると要求が `PROCESSING` のまま残る(→復旧処理が必要) |
| B. 非同期処理: 202 Accepted を返し、バックグラウンドで処理。クライアントは GET でポーリング | 応答が速い。長い処理に向く                                                | ワーカー(プロセス内ループ or キュー)が必要。「処理中に落ちたら」の設計が必須で複雑                      |
| C. メッセージキュー(SQS 等)                                                                 | 本格的な耐障害性                                                          | 要件で「安易に導入しない」。学習対象外のインフラ                                                        |

## 決定: A

- 最悪の応答時間は、`タイムアウト × 試行回数 + バックオフ`(既定: 10秒 × 4回 + 待機 ≒ 数十秒)に**設計上、上限がある**
- ただし A でも「状態を DB に残す」ので、`GET /v1/repository-requests/{id}` で処理状態を確認できる(要件B・C)
- 処理中の中断(プロセス終了・DB保存失敗)は、**リース(`PROCESSING_LEASE_MS`、既定5分)切れ後に復旧**する(ADR-0007)
  - リースは「最悪の処理時間」より十分長くする(短いと、まだ動いている処理を「中断した」と誤判定する)
- 将来 B に変える場合も、`ProvisioningService.process()` を呼ぶ場所が変わるだけで、状態遷移・冪等性・復旧は再利用できる

## 結果

- クライアントは同期で結果を得られるが、タイムアウトを長めに設定する必要がある(推奨: 60秒以上)
- 水平スケール(複数プロセス)は想定しない(SQLite のローカルファイル)。複数にするなら DB を変え、B を検討する
