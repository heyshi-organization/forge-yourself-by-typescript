# ADR-0007: 冪等性の実現方法

- 状態: 採用
- 日付: 2026-11-25

## 背景

「同じリクエストが重複して送信されても、意図しない重複作成が起きない」。
単にHTTPの再送が安全というだけでなく、**外部API呼び出しの途中で障害が起きた場合**も設計する。

起こりうる失敗(時系列):

```
(1) 要求をDBに保存 → (2) PROCESSING にする → (3) GitHub にリポジトリ作成を依頼 → (4) 結果をDBに保存
   ↑プロセスが落ちる      ↑落ちる             ↑タイムアウト/落ちる(作られたか不明)   ↑DB保存に失敗(GitHubでは作成済み)
```

## 選択肢

| 案                                                  | 内容       | 評価                                                                 |
| --------------------------------------------------- | ---------- | -------------------------------------------------------------------- |
| A. 事前の存在確認だけ(GETして無ければ作成)          | 実装が簡単 | **競合に弱い**(確認と作成の間に別の要求が割り込む)。途中障害にも無力 |
| B. DBのUNIQUE制約だけ                               | 競合に強い | 途中障害(3)(4)の扱いが無い                                           |
| C. **Idempotency-Key + 状態機械 + 復旧(reconcile)** | 下記       | 実装は多いが、すべての失敗点に答えがある                             |

## 決定: C

### 1. 受付(重複の排除)

- クライアントは `Idempotency-Key` ヘッダを必ず付ける(8〜128文字の `[A-Za-z0-9_-]`。UUIDを推奨)
- `createOrGet`: キーが無ければ `PENDING` で保存、あれば既存を返す。**トランザクション内**で行い、`idempotency_key` の **UNIQUE制約**が最後の砦
- 要求内容のSHA-256(`request_hash`。topicsの順序は無視)を保存する。**同じキーで内容が違えば 422** `IDEMPOTENCY_KEY_REUSED`(キーの使い回しバグの検出)
- 別のキーでも、**同じ owner/name の処理中要求は1件**(部分ユニークインデックス)→ 409 `REPOSITORY_REQUEST_IN_PROGRESS`

### 2. 再送の結果

| 保存済みの状態                     | 再送したときの応答                                                                        |
| ---------------------------------- | ----------------------------------------------------------------------------------------- |
| `SUCCEEDED`                        | 200 + `Idempotent-Replayed: true`。**GitHubは呼ばない**                                   |
| `FAILED`                           | 同じ失敗を再現(`Idempotent-Replayed: true`)。**再実行しない**。やり直すには**新しいキー** |
| `PENDING`/`PROCESSING`(リース内)   | 409 `REQUEST_IN_PROGRESS` + `Retry-After`                                                 |
| `PENDING`/`PROCESSING`(リース切れ) | 復旧処理(下記)を行ってから応答                                                            |

`FAILED` を再実行しないのは、「同じキー = 同じ結果」という約束を単純に保つため(Stripe等と同じ考え方)。

### 3. 状態遷移の原子性(二重実行の防止)

`transition(id, from, target)` は SQL の `UPDATE ... WHERE id = ? AND status = ?`(**compare-and-set**)。
同じ要求を2つの処理が同時に進めようとしても、先に `PENDING→PROCESSING` にできた1つだけが実行権を得る(負けた方は 0行更新=`null`)。

### 4. 中断からの復旧(reconcile)

`PROCESSING`/`PENDING` のまま `updated_at` から**リース時間**(既定5分)が過ぎた要求を「中断された」とみなす(起動時と、同じキーの再送時に検出)。

- `PENDING`: GitHubをまだ呼んでいない → 通常どおり処理する
- `PROCESSING`: GitHubを呼んだかもしれない → **GitHubを確認(reconcile)**
  - リポジトリがあり、**作成日時が「今回の処理の開始時刻(−許容60秒)」以降** → 今回作られたもの → `SUCCEEDED`(topicsも再設定。PUTなので冪等)
  - あるが古い → 以前からあった別物 → `FAILED(REPOSITORY_ALREADY_EXISTS)`
  - 無い → `FAILED(INTERRUPTED)`。**自動で再作成はしない**(判断をクライアントに返す。新しいキーで再送できる)

### 5. 受け入れるトレードオフ

- 「作成日時で今回の処理のものか判定」は**ヒューリスティック**。時計のずれ(許容幅60秒)内に、第三者が同名のリポジトリを作った場合は誤判定しうる
  (リポジトリ名の重複自体がGitHub側で防がれるため、実害が出る条件はかなり狭い)。GitHub側にタグ付け等の仕組みが無いための現実的な妥協
- 複数プロセスから同じDBを使う場合、リース切れ直後の復旧が競合しうる。ただし状態更新は compare-and-set なので、**二重にGitHubを呼ぶことはあっても、結果が二重に確定することはない**(2つ目は conflict になり reconcile で吸収)

## 結果

すべての失敗点(上の図の4か所)に対して、テストがある(`exercises/tests/ex10-idempotency.test.ts`、`reference/test/http/api.test.ts`)。
