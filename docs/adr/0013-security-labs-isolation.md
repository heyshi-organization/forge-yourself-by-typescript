# ADR-0013: セキュリティ演習(意図的に脆弱なコード)の隔離

- 状態: 採用
- 日付: 2026-11-25

## 背景

要件: 脆弱なコードは (1) 通常のアプリから分離する (2) 通常のアプリから実行できない (3) **main にマージしない** (4) 公開環境で攻撃を試す構成にしない
(5) 実際の秘密情報を使わない。一方で、CodeQL が**実際に検出する様子**を学習者に体験させたい。

「専用ディレクトリ」と「main にマージしない」は両立が難しい(ディレクトリに置けば main に入る)ので、次のように設計した。

## 選択肢

| 案                                                                               | 評価                                                                                              |
| -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| A. `security-labs/` に `.ts` として置く                                          | main に脆弱な実行可能コードが入る。ビルド・lint・CodeQL の対象になり、CIも混乱する                |
| B. 演習ごとの長期ブランチに置く                                                  | main に脆弱コードは入らないが、教材(README)と分離され、学習者が見つけにくい。ブランチの維持が大変 |
| C. **main には `.txt` で保管し、学習者が自分の `exercise/*` ブランチに展開する** | main の脆弱コードは実行・ビルド・解析のどれの対象にもならない。教材は main に集約できる           |

## 決定: C

1. `security-labs/<演習>/vulnerable/app.ts.txt`(脆弱版)・`solution/app.ts.txt`(修正版)・`security.test.ts.txt`(攻撃を防ぐテスト)を `.txt` で保管
   - `.txt` なので `tsc` / ESLint / Prettier / CodeQL / Vitest のどれにも拾われない。`import` もできない
2. `npm run lab:start -- <演習>` が、`exercise/sec-<演習>` ブランチを作り、`lab-workspace/<演習>/` に `.ts` として展開する
   - 学習者は修正してテストを通し、**ドラフトPR**を作って CodeQL の結果を見る
3. **ガード**: `exercise-guard.yml` が、`exercise/*` ブランチの PR と `lab-workspace/` を含む PR を**必ず失敗**させる(→ 必須ステータスチェックにしてあればマージできない)
4. 演習の健全性は `npm run lab:verify` が検証する(CIで実行): 脆弱版では「正常な利用」のテストは通り、攻撃を防ぐテストが失敗する / 修正版は全部通る
   - 検証は `.lab-work/`(gitignore)で行い、コミットされない
5. 脆弱なコードは**ローカルのテストでしか動かない**(HTTPサーバーとして起動する入口を作らない。`app.inject()` のみ)。ネットワークに公開しない
6. ダミーの秘密は明らかな偽物(`lab-dummy-...`)。Secret Scanning の検証に実在トークンは使わない

## 結果

- main は常に健全。演習ブランチは使い捨て(PRを閉じて削除する)
- 受け入れるトレードオフ: 学習者が `lab:start` を一度実行する手間
